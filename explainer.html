Implementation explainer

Tracking a ball through a moving eight-slot conveyor

The simulator treats the conveyor position as the identity signal. That is deliberately simple and deterministic for a synthetic camera, while making the boundary between a laboratory model and a production inspection system clear.

Identity across eight appearances

Every station owns eight fixed BucketSlot positions. On each trigger, ConveyorStation::onTrigger shifts the existing contents one position to the right and spawns a new position at slot 0. A physical ball therefore appears at slots 0 through 7, one observation per trigger, before it exits.

StationWorker keeps a BallTrack containing a generated track ID, its current slot, observation count, and measurements. For slot i, the worker inherits the track from slot i - 1; the contents leaving slot 7 are finalized. Color, radius, and diameter are averaged, while defect observations are combined by majority vote.

Empty and neighboring slots

An empty bucket is represented by detectedBall == false. It creates no track and contributes no observation. Because every ROI is tied to one known slot, two adjacent balls are kept separate even when their colors or sizes are similar: slot 2 can only inherit slot 1, never slot 3 or a global “nearest” candidate.

Simulation boundary. This positional identity is reliable when triggers are not missed, ROIs are aligned, and balls move exactly one slot per trigger. If a ball is not detected for a frame, the current implementation cannot bridge the gap; a later detection starts a new track. The generated trueId is not used by the worker, so this is positional tracking rather than hidden ground-truth matching.

Scaling to twelve stations

The pipeline is parameterized by stationCount. ConveyorManager creates one station, worker, and QThread per entry, then loops over the collection for startup, triggering, metrics, and shutdown. Changing construction from ConveyorManager(3) to ConveyorManager(12) needs no tracking redesign.

Each station has its own ID, timer, trigger counter, slots, and tracks. The default timers are staggered by station index, and metrics are keyed by that ID rather than by a fixed three-station array. The UI would still need product changes: it currently displays only station 0 and contains three-station status wording. At larger counts, a bounded worker pool could also be considered instead of one thread per station.

Synchronization and race risks

Each station and its worker live in the same Qt thread, so frame processing and track mutation are serialized by that thread’s event loop. Track state has one owner and does not require a mutex. QImage and verdict data are passed by value, and BallFusedVerdict is registered for queued signal delivery.

Shutdown stops timers, flushes active tracks with a blocking queued call, then quits and waits for each thread. The manager and UI receive cross-thread callbacks through queued delivery.

Remaining caveat. The worker’s frame callback is connected before the manager’s timing callback. Processing can therefore complete before the manager records the frame start, leaving latency or pending-frame metrics without a matching timestamp. Manual triggers can also interleave with timer events, and starting pipelines repeatedly creates additional timers.

From simulation to camera and PLC

The simulator produces one perfectly aligned synthetic 800 × 120 frame synchronously for each timer or manual trigger. It assumes a local monotonic trigger index, fixed bucket ROIs, no exposure delay, and no dropped, duplicated, delayed, or out-of-order frames.

A real camera/PLC integration would need hardware timestamps or sequence numbers, trigger debouncing, bounded queues, backpressure, and explicit handling for late or missing frames. Camera calibration would locate bucket boundaries and detect drift; exposure and readout jitter could place a frame between bucket positions. Misaligned or partially visible buckets would require confidence checks and an unresolved-frame policy rather than silently creating a new track.

For continuity across a missed observation, the system would need an encoder/PLC position, persistent object IDs, or motion-and-appearance matching. If several stations inspect the same ball, their timestamps and IDs would also need a cross-station correlation layer. The current capturer class is only a stub, so these hardware concerns are intentionally outside the simulator.
